## 1. 통신 방식 비교 (WebRTC 등)

### 후보 비교

| 방식 | 방향 | 특징 | 이 과제에 대한 적합성 |
|---|---|---|---|
| **폴링** (REST 주기 호출) | 클라이언트 → 서버 | 구현 가장 단순 | 지연이 폴링 주기만큼 생기고, 새 메시지가 없어도 요청이 계속 발생 |
| **SSE** (Server-Sent Events) | 서버 → 클라이언트 (단방향) | HTTP 위에서 동작, 자동 재연결, `Last-Event-ID` 지원 | 수신은 좋지만 송신은 별도 REST 필요 |
| **WebSocket** (채택) | 양방향 | 연결 하나로 송수신, 메시지 형식 자유 | ACK, 재전송, RESUME 프로토콜을 직접 설계해 보여줄 수 있음 |
| STOMP over WebSocket | 양방향 | 구독/발행, 특정 사용자 전송, 하트비트, 외부 브로커 릴레이로 여러 서버 간 전달 | 서버 한 대 범위에서는 순수 WebSocket으로 충분했다. 다중 서버로 확장할 때는 Redis Pub/Sub(5 §5) 대신 STOMP + 외부 브로커도 대안 |
| **WebRTC** | 사용자 ↔ 사용자 (P2P) | 지연이 가장 짧고 서버 부하가 작음. 연결 수립에 시그널링 서버가 필요하고, NAT, 방화벽 때문에 직접 연결이 안 되면 TURN 중계 서버도 필요 | 아래 참고 |

### WebRTC(P2P)를 채택하지 않은 이유

| 요구사항 | 서버 중계 (채택) | P2P |
|---|---|---|
| 순서 기준 | 서버가 seq를 한 곳에서 발급 | 양쪽이 각자 기록 → 전체 순서 합의가 어려움 |
| 중복 방지 | 서버가 `clientEventId`로 필터 | 각 클라이언트가 처리 |
| 이벤트 저장, 시점 복원 | 서버 DB에 기록 | 별도로 서버에 업로드해야 하고, 업로드 누락 시 복원 불가 |
| 상대가 오프라인일 때 | 서버가 보관 후 재연결 시 전달 | 전달 불가 |

과제의 핵심 요구(순서, 중복, 복원)가 모두 **단일 기준점**을 필요로 하므로 서버 중계 방식을 택했다.
영상, 음성 통화처럼 대용량 저지연 미디어가 필요해지면, **메시지, 이벤트는 서버 중계로 유지하고 미디어만 WebRTC로 분리**하는 병행 구조가 적합하다. 이때 WebSocket 연결을 시그널링 채널로 재사용할 수 있다.

## 2. 테스트 전략

| 수준 | 도구 | 내용 |
|---|---|---|
| 통합 테스트 | JUnit 5 + **Testcontainers (MySQL 8.4)** | `./gradlew test` 한 번으로 실행. 테스트할 때 Docker로 실제 MySQL 8.4를 띄운다. 이 프로젝트의 핵심이 MySQL의 락 동작이라, 다른 DB(H2 같은 메모리 DB)로 테스트하면 통과해도 실제 MySQL에서 같게 동작한다고 보장할 수 없기 때문 |
| 장애 주입 실험 | 락 제거 후 동시성 테스트 실행 | 락이 없으면 seq 중복(`uk_event_seq` 위반)과 데드락이 발생함을 확인 → 테스트가 실제로 락을 검증함을 증명 ([5 §9](5-design.md#9-검증-결과-순서-중복-동시성)) |
| 재현 스크립트 | `scripts/concurrency-test.sh` | curl 20개 동시 전송, 동시 재전송으로 HTTP 수준 검증 |
| 성능 측정 | `scripts/seed-perf.sql` | 세션 10만, 이벤트 10만 건으로 `EXPLAIN ANALYZE` 실측 |

**통합 테스트 목록** (각 결과의 해석은 해당 기능 문서에 있다)

| 테스트 | 검증 내용 |
|---|---|
| [재전송 멱등](5-design.md#9-검증-결과-순서-중복-동시성) | 같은 `clientEventId` → 같은 seq, 저장 1건 |
| [같은 키 다른 내용](5-design.md#9-검증-결과-순서-중복-동시성) | 409 (ConflictException) |
| [종료 후 재전송](5-design.md#9-검증-결과-순서-중복-동시성) | 중복 확인이 검증보다 먼저 → 최초 결과 반환 |
| [동시 전송 20개](5-design.md#9-검증-결과-순서-중복-동시성) | seq 빈틈, 중복 없음 |
| [동시 재전송 20개](5-design.md#9-검증-결과-순서-중복-동시성) | 1건만 저장, 모두 같은 seq |
| [복원 결정성](6-state-restoration.md#7-검증-결과) | 모든 시점에서 2회 복원 결과 동일 |
| [프로젝션 = 리플레이](6-state-restoration.md#7-검증-결과) | 참여자 테이블 = 이벤트 리플레이 결과 (상태 테이블은 재생성 가능) |
| [스냅샷 = 전체 리플레이](6-state-restoration.md#7-검증-결과) | 스냅샷이 주기마다 비동기 생성되고, 스냅샷 기반 복원이 모든 시점에서 전체 리플레이와 같음 |
| 컨텍스트 로딩 | 애플리케이션 기동 |

설계 원칙: 테스트 클래스에 `@Transactional`을 붙이지 않는다. 동시성 테스트의 각 스레드가 커밋된 데이터를 봐야 하고 `AFTER_COMMIT` 흐름이 운영과 같아야 하기 때문이다. 대신 테스트마다 새 세션을 만들어 격리한다. 비동기 결과는 최대 5초 폴링으로 기다린다.

## 3. 부하 테스트, 대시보드

**미실시 / 설계만** — 제출 기한 내 우선순위에서 제외했다. 계획은 다음과 같다.

| 항목 | 계획 |
|---|---|
| 부하 시나리오 (k6) | 세션 N개 × 참여자 2명이 WebSocket으로 초당 M건 전송. 같은 `clientEventId` 재전송을 일정 비율 섞음 |
| 측정 지표 | ACK 지연 p50/p95/p99, 처리량, 503(락 대기 초과) 비율, 중복 저장 0건 확인 |
| 예상 병목 | 세션 행 락은 세션 단위로만 직렬화되므로 세션 수에 비례해 확장, 결국 DB 쓰기와 커넥션 풀이 한계 ([5 §5 병목 예상](5-design.md#5-서버-수평-확장--설계)) |
| 메트릭 (Micrometer → Prometheus) | 이벤트 저장 수, 지연(Timer), 중복 수신 수, 락 대기 시간, 503 수, WebSocket 연결 수(Gauge), 스냅샷 생성 시간, 실패 수 |
| 대시보드 (Grafana) | 위 메트릭 + HikariCP 커넥션 대기, JVM 지표 |
