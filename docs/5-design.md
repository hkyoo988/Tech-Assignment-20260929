## 1. 실시간 메시지 전달 구조 — 구현 완료

```
alice ══WS══╗                                    ╔══WS══ bob
            ▼                                    ║
  ChatWebSocketHandler                           ║
    └ EventService.append()   @Transactional     ║
        └ saveEvent()                            ║
            ├ INSERT session_event               ║
            └ publishEvent(EventAppended)        ║   ← 커밋 후 실행 예약
        ── COMMIT ──                             ║
            └ EventBroadcaster.on()  @TransactionalEventListener(AFTER_COMMIT)
                └ WebSocketSessionRegistry.broadcast(보낸 사람 제외) ─┘ EVENT
    └ 보낸 사람에게 ACK
```

| 구성 요소 | 역할                                                                                                          |
|---|-------------------------------------------------------------------------------------------------------------|
| `ChatWebSocketHandler` | 연결/수신/종료 처리. 메시지를 `append()`로 넘기고 ACK, ERROR 응답                                                             |
| `WebSocketSessionRegistry` | 세션별 연결 목록 (메모리, `ConcurrentHashMap`). 연결마다 `ConcurrentWebSocketSessionDecorator`로 감싸 **여러 스레드의 동시 전송을 직렬화** |
| `EventBroadcaster` | 커밋 후 이벤트를 받아 상대 연결로 전송                                                                                      |

**설계 포인트**
- **커밋 후 전달**: 롤백된 이벤트가 상대 화면에 보이지 않는다. "상대가 본 메시지는 반드시 DB에 있다"가 보장된다.
- **입구와 무관**: 발행이 `saveEvent()` 안에 있어 REST로 들어온 이벤트(예: REST `/leave`)도 WebSocket 연결에 전달된다.
- **의존 방향**: `event` 패키지는 `realtime` 패키지를 모른다(Spring 이벤트로 느슨하게 연결).
- **클라이언트-서버 구조**: 사용자끼리 직접 연결하지 않고 서버가 중계한다. 순서(seq), 중복 제거, 저장, 복원이 모두 서버에서 일어나야 하기 때문 (P2P 비교는 [7-optional.md#1-통신-방식-비교-webrtc-등](7-optional.md#1-통신-방식-비교-webrtc-등)).

**한계**

| 한계 | 영향 | 보완 |
|---|---|---|
| 전송이 커밋 스레드에서 동기 실행 | 상대 전송이 느리면 보낸 사람의 ACK도 지연 | `@Async` 리스너로 분리 ([5 §7](5-design.md#7-비동기-처리-구조--일부-구현-스냅샷)) |
| 커밋 후 전송 실패 시 재시도 없음 | 상대가 이벤트를 놓칠 수 있음 | **재연결 시 RESUME으로 보완** ([5 §4](5-design.md#4-재연결-시-정합성--구현-완료)). 실시간 경로는 best-effort, 정합성은 RESUME이 책임 |
| 연결 목록이 서버 메모리 | 서버 2대 이상이면 상대가 다른 서버에 있을 때 전달 불가 | 서버 간 Pub/Sub ([5 §5](5-design.md#5-서버-수평-확장--설계)) |

## 2. join / leave, presence, 이벤트 수집 API — 구현 완료

**join / leave**: 전용 엔드포인트(`POST /sessions/{id}/join`, `/leave`, `/end`)와 WebSocket 메시지(`JOINED`, `LEFT`)가 모두 `EventService.append()`라는 **하나의 경로**로 들어간다. 입구가 달라도 락, 멱등, 순서 규칙이 같다. 퇴장(`LEFT`)해도 WebSocket 연결은 유지되며 같은 연결로 다시 입장할 수 있다.

**presence**: 참여 상태와 접속 상태를 **두 필드로 분리**한다.

| 필드 | 답하는 질문 | 바뀌는 계기 |
|---|---|---|
| `state` (JOINED / LEFT) | 방에 들어와 있나? | 사용자가 **의도적으로** 입장, 퇴장 (클라이언트가 보내는 `JOINED`/`LEFT`) |
| `presence` (ONLINE / OFFLINE) | **이 대화방에 지금 접속해 있나?** | 사용자 의도와 무관하게 **연결이 끊기거나 다시 붙음** (서버가 기록하는 `DISCONNECTED`/`RECONNECTED`) |

presence의 정의는 "참여 중인 사람이 이 대화방에 지금 접속해 있는가"다. 메신저 대화방에서 상대 이름 옆의 초록 점, 회색 점에 해당하며, 앱 전체의 접속 여부가 아니라 **대화방 기준**이다. 입장하면 ONLINE, 참여 중 연결이 끊기면 OFFLINE, 다시 연결되면 ONLINE이 되고, **퇴장한 사람은 소켓 연결과 무관하게 OFFLINE**이다(대화방에 없으므로).

**실제 서비스 시나리오** — 중고거래 1:1 채팅, bob(구매자)이 alice(판매자)에게 말을 거는 경우

| # | 사용자 행동 | 앱 → 서버 | 기록되는 이벤트 | alice (state / presence) | bob 화면 |
|---|---|---|---|---|---|
| 1 | bob이 상품 페이지에서 "채팅하기" | 세션 생성 | `SESSION_STARTED` | LEFT / OFFLINE | 빈 채팅방 |
| 2 | bob의 채팅방 화면이 열림 | 소켓 연결 + 입장 | `JOINED`(bob) | LEFT / OFFLINE | |
| 3 | alice가 알림을 보고 채팅방을 엶 | 소켓 연결 + 입장 | `JOINED`(alice) | **JOINED / ONLINE** | alice 옆 초록 점 |
| 4 | 가격 흥정 | 메시지 전송 | `MESSAGE_SENT` ×N | JOINED / ONLINE | 실시간 대화 |
| 5 | alice가 지하철에서 **신호 끊김** | (서버가 소켓 끊김 감지) | `DISCONNECTED` | JOINED / **OFFLINE** | alice 옆 회색 점 "잠시 오프라인" |
| 6 | bob이 "내일 7시 가능?" 전송 | 메시지 전송 | `MESSAGE_SENT` | JOINED / OFFLINE | 저장됨, alice는 아직 못 받음 |
| 7 | alice **신호 회복** | 자동 재연결 (`lastSeq` 전달) | `RECONNECTED` | JOINED / **ONLINE** | 다시 초록 점. alice 화면에 놓친 메시지가 RESUME으로 채워짐 (§4) |
| 8 | alice가 **"채팅방 나가기"** | 퇴장 → 앱이 채팅 화면을 닫으며 소켓도 끊음 | `LEFT` | **LEFT** / OFFLINE | "alice님이 대화방을 나갔습니다" |
| 9 | 거래 완료 | 세션 종료 | `SESSION_ENDED` | | 서버가 모든 연결을 닫음, 읽기 전용 |
| 10 | 한 달 뒤 bob이 "7시라고 했잖아요" 신고 | 운영자가 `GET /timeline?at=…` | (조회만) | | 6번 시점의 대화, 접속 상태를 그대로 확인 ([6 상태 복원](6-state-restoration.md)) |

- 5번(JOINED / OFFLINE)과 8번(LEFT / OFFLINE)은 상대 화면에서 다르게 보여야 한다. 5번은 "잠시 오프라인 — 보낸 메시지는 나중에 받음", 8번은 "대화를 떠남". 필드가 하나라면 둘을 구분할 수 없다.
- 퇴장해도 서버는 연결을 강제로 끊지 않는다. 끊을지는 클라이언트가 정하며, 같은 연결로 재입장하거나 이벤트를 계속 받을 수 있다.

## 3. 순서 기준과 중복 처리 — 구현 완료

### 문제 정의: 순서와 중복

| 제약 | 실제로 일어나는 상황 |
|---|---|
| 중복 전송 | 클라이언트가 보냈지만 ACK를 못 받음(네트워크 끊김) → 같은 이벤트 재전송 |
| 순서 뒤바뀜 | 메시지 A, B를 연달아 보냈는데 B가 먼저 도착 / 재전송된 A가 B보다 늦게 도착 |

서버는 도착(커밋) 순서로 seq를 매기므로 A, B가 뒤바뀐 채 기록될 수 있다. 대신 두 참여자가 **항상 같은 순서**를 보고, 복원도 이 순서를 따른다.

### 순서 기준: 세션별 서버 seq

- **정의**: 한 세션 안에서 서버가 이벤트를 **커밋한 순서**대로 1, 2, 3 … 을 부여한다. 이 값이 유일한 순서 기준이다.
- **발급 방법**: 이벤트 저장 트랜잭션에서 세션 row를 `SELECT ... FOR UPDATE`로 잠그고 `last_seq + 1`을 발급한 뒤, 이벤트 INSERT와 `last_seq` UPDATE를 함께 커밋한다.
- **보장**: 같은 세션의 이벤트는 한 번에 하나씩 seq를 받으므로 **빈 번호도, 겹치는 번호도 없다**. `UNIQUE(session_id, seq)`가 최후 방어선이다.
- `clientTs`는 저장하지만 정렬에 쓰지 않는다 (기기 시계 오차, 조작 가능성).
- `serverTs`도 정렬에 쓰지 않는다. 서버가 여러 대면 시계 차이로 seq 순서와 어긋날 수 있다. 세션 내 단조 보정(직전보다 작으면 직전 값으로 맞춤)은 **미적용**이며 §10에 개선 방향으로 남겼다.

#### 상태에 맞지 않는 이벤트 거부

| 상황 | 처리 |
|---|---|
| 입장(`JOINED`) 상태가 아닌 사용자의 `MESSAGE_SENT` | 거부 (409) |
| `SESSION_ENDED` 이후 모든 이벤트 | 거부 (409) |

### 중복 처리: 멱등 키

- 클라이언트는 이벤트마다 `clientEventId`(UUID)를 만들고, **재전송할 때 같은 값을 쓴다**.
- 저장 흐름:
  1. 세션 락 획득
  2. `(session_id, client_event_id)`로 기존 이벤트 조회
  3. 있으면 → 내용 비교 후 동일하면 **기존 이벤트를 200으로 반환** (seq 새로 발급 안 함), 다르면 409
  4. 없으면 → seq 발급, INSERT
- 락 안에서 확인하므로 동시에 같은 키 두 개가 들어와도 하나만 저장된다. `UNIQUE(session_id, client_event_id)`는 락 밖 경로(버그, 수동 입력)에 대비한 최후 방어선.

#### 왜 409가 아니라 200으로 돌려주나

재전송은 클라이언트 입장에서 "내 이벤트가 저장됐는지 모르는 상태"다. 에러를 주면 클라이언트가 실패로 오해하고 다시 재시도하거나 사용자에게 실패를 표시한다. **같은 요청에는 같은 응답**을 주는 것이 멱등성의 정의다.

### 다층 방어

| 층 | 장치 | 막는 것 |
|---|---|---|
| 클라이언트 | `clientEventId` 재사용, ACK 받을 때까지 재전송 | 유실 |
| 서버 로직 | 락 + 기존 이벤트 조회 | 중복 저장, seq 중복 |
| DB 제약 | UNIQUE 2개 | 로직을 우회한 중복 |
| 복원 로직 | seq 오름차순, `seq ≤ lastApplied`면 건너뜀 | 프로젝션 중복 반영 |

### 처리 순서와 그 이유 (구현)

```
EventService.append()   @Transactional
 ① SELECT ... FROM chat_session WHERE id=? FOR UPDATE      세션 행 락
 ② SELECT ... FROM session_event
      WHERE session_id=? AND client_event_id=?              중복 확인
      → 있으면: 내용 같으면 최초 결과 반환(200), 다르면 409
 ③ 검증: 참여자인가, 서버 전용 타입인가, 종료된 세션인가, 메시지면 JOINED인가
 ④ seq 발급(last_seq+1) → INSERT session_event → 참여자 프로젝션 갱신
    → 커밋 시 UPDATE chat_session.last_seq
```

| 순서 | 어기면 생기는 문제 |
|---|---|
| ②를 ① **뒤에** (락을 잡은 상태에서) | 락 없이 확인하면 동시에 온 재전송들이 모두 "없음"으로 판단(Check-Then-Act 경쟁) → 둘 다 INSERT 시도 → 하나는 UNIQUE 위반으로 에러. 이미 저장된 이벤트인데 클라이언트는 실패로 인식 |
| ②를 ③ **앞에서** | 최초 요청 후 세션이 종료되거나 사용자가 퇴장한 뒤 재전송이 오면, 검증에서 에러가 난다. 이미 저장된 이벤트인데 클라이언트는 실패로 인식 |

## 4. 재연결 시 정합성 — 구현 완료

**목표**: 연결이 끊겼다 돌아온 클라이언트가 그사이 생긴 이벤트를 하나도 놓치지 않고 따라잡는다.

**방법**: 클라이언트가 마지막으로 받은 seq(`lastSeq`)를 들고 재연결하면, 서버가 그 이후 이벤트를 한 번에 보낸다(RESUME).

```
bob 연결 끊김
  └ 서버: DISCONNECTED 기록 (seq 6, presence → OFFLINE) → alice에게 EVENT
alice: 메시지 seq 7, 8 → bob은 연결이 없어 못 받음 (DB에는 저장)
bob 재연결: ws://…?sessionId=…&userId=bob&lastSeq=5
  ① 참여자 확인
  ② 연결 등록           ← 이후 실시간 EVENT 수신 시작
  ③ RECONNECTED 기록    (seq 9, presence → ONLINE) → alice에게 EVENT
  ④ seq > 5 이벤트 조회 → RESUME [6, 7, 8, 9] 전송
```

받은 위치를 서버가 아니라 클라이언트가 알려 주는 이유: 서버는 어디까지 보냈는지만 알고, 실제로 받았는지는 받은 쪽이 가장 정확히 안다. 서버가 위치를 저장하지 않으니 전송할 때마다 쓰기가 생기지도 않는다.

**누락, 중복이 생기지 않는 이유**

| 위험 | 막는 방법 |
|---|---|
| 조회와 등록 사이에 생긴 이벤트를 놓침 | 연결 등록(②)을 조회(④)보다 먼저 한다. 그사이 생긴 이벤트는 실시간 EVENT와 RESUME 양쪽으로 와서, 중복은 생겨도 누락은 없다 |
| 같은 이벤트를 두 번 받음 | 클라이언트가 받은 최대 seq 이하는 무시한다 |
| 내가 보낸 이벤트가 저장됐는지 모름 | ACK를 못 받았으면 같은 `clientEventId`로 재전송한다. 서버는 한 번만 저장한다 |
| 놓친 이벤트가 너무 많음 | RESUME은 최대 500건이다. `hasMore=true`면 `GET /events?afterSeq=`로 이어서 조회한다 |

## 5. 서버 수평 확장 — 설계

| 대상 | 단일 서버 (현재) | 다중 서버 |
|---|---|---|
| seq 발급, 중복 확인 | DB 행 락 | **그대로** (DB가 단일 기준이라 서버 수와 무관) |
| 연결 목록 | 서버 메모리 | 서버마다 자기 연결만 보유 |
| 실시간 전달 | 메모리에서 찾아 전송 | 커밋 후 **Redis Pub/Sub 채널 `session:{id}`**에 발행 → 모든 서버가 구독해 자기 연결에만 전송 |
| presence | 이벤트 + 참여자 테이블 | 동일. 연결 여부의 실시간 캐시가 필요하면 Redis에 TTL 키 |

병목 예상: 한 세션의 쓰기는 행 락으로 직렬화되지만, 1:1 채팅은 세션당 쓰기 빈도가 낮아 문제가 적다. 전체 처리량은 세션 수에 따라 수평 확장되고, 결국 DB 쓰기가 한계가 된다 → 세션 id 해시 기반 샤딩, 오래된 이벤트 아카이빙.

## 7. 비동기 처리 구조 — 일부 구현 (스냅샷)

| 대상 | 현재 | 계획 |
|---|---|---|
| 참여자 프로젝션 | 이벤트와 같은 트랜잭션에서 동기 갱신 | **동기 유지**. 메시지 전송 시 JOINED 확인에 쓰므로, 늦게 반영되면 틀린 상태로 판단한다 |
| 스냅샷 생성 | **구현**: 100개마다, 세션 종료 시 커밋 후 `@Async` 생성, `INSERT IGNORE`로 멱등, 실패 시 로그 후 리플레이로 대체 | 스레드 수 상한(`max-size`) 설정 (아래) |
| 실시간 전달 | AFTER_COMMIT 동기 | `@Async`로 분리 |
| 재시도 / DLQ | 없음. 현재 비동기 작업(스냅샷)은 놓쳐도 다음 주기와 리플레이가 메우므로 재시도가 필요 없다 | 놓치면 안 되는 비동기 작업이 생기면 지수 백오프 재시도(예: 1s, 2s, 4s, 최대 5회) → 실패 시 DLQ 테이블에 기록 후 운영자 재처리 |
| 유실 방지 | 커밋 후 서버가 죽으면 전송, 스냅샷 작업이 사라진다. 하지만 이벤트는 DB에 있으므로 전송은 RESUME이, 스냅샷은 리플레이가 메운다 | 놓치면 메울 방법이 없는 작업(푸시 알림, 외부 연동)이 생기면 **Outbox 패턴**: 이벤트와 같은 트랜잭션에 할 일 행을 기록하고 워커가 처리 |
| 중복 실행 (Idempotency) | 스냅샷은 PK `(session_id, seq)` + `INSERT IGNORE`로 1건만 남음. 프로젝션은 `last_applied_seq` 이하 seq를 무시 | 재시도, 다중 서버에서 같은 작업이 두 번 실행돼도 그대로 안전 |

**스레드 풀**: 스냅샷 `@Async`는 Spring Boot 기본 풀(스레드 8개)을 쓴다. 대기열은 `queue-capacity: 1000`으로 제한했다. 단 스레드 수 상한(`max-size`) 기본값이 무제한이라 대기열이 차면 스레드가 계속 늘어나므로, `max-size`도 지정해야 넘치는 작업이 버려진다.

## 8. 장애 대응 시나리오 (감지 → 완화 → 복구)

### ① 데이터 유실 / 정합성 이슈 (중복 저장, 부분 실패)

| 단계 | 내용 |
|---|---|
| **예방 (구현됨)** | 중복 저장: 락 안 중복 확인 + DB UNIQUE 2개(`uk_event_client_id`, `uk_event_seq`)로 이중 방어 — 동시 재전송 테스트로 검증. 부분 실패: 이벤트 INSERT, 참여자 갱신, `last_seq` 갱신이 **한 트랜잭션** → 전부 성공 또는 전부 롤백 |
| **감지** | ① 정합성 점검 쿼리를 주기 실행: `chat_session.last_seq ≠ MAX(session_event.seq)`인 세션, `session_participant`와 리플레이 결과가 다른 세션 ② `DataIntegrityViolation` 발생 수 메트릭 — 정상 흐름에서는 0이어야 하므로 1건이라도 나오면 경보 ③ `[스냅샷 실패]` 로그 수 |
| **완화** | 원본은 이벤트이므로 **파생 데이터만 의심**한다. 불일치 세션의 조회는 상태 테이블 대신 리플레이 결과로 응답하도록 전환. 클라이언트는 같은 `clientEventId`로 재전송하면 안전하므로 실패 응답에 재시도 안내 |
| **복구** | 상태 테이블(`session_participant`, `chat_session.status/last_seq`)을 **이벤트 리플레이로 재생성**. 잘못된 스냅샷은 삭제 후 재생성 — 스냅샷이 없어도 복원은 리플레이로 정답이므로 삭제가 안전. 이벤트 자체가 잘못 기록된 경우는 수정, 삭제하지 않고 **보정 이벤트를 추가**(append-only 원칙) |

### ② 서버 다운 (인스턴스 장애)

| 단계 | 내용 |
|---|---|
| **감지** | `/actuator/health` 실패, 인스턴스별 WebSocket 연결 수 급감, 5xx 비율 증가 |
| **완화** | 로드밸런서가 장애 인스턴스를 제외. 클라이언트는 지수 백오프(1s, 2s, 4s… 상한)로 재연결. DB가 단일 기준이라 다른 인스턴스가 즉시 같은 세션을 처리할 수 있음(seq 발급, 중복 확인이 서버 메모리에 없음) |
| **복구** | 재연결 시 `lastSeq`로 **RESUME** → 끊긴 동안의 이벤트 누락 없음. 커밋 전이던 요청은 롤백되어 ACK가 없으므로 클라이언트가 같은 `clientEventId`로 재전송 → 멱등 처리. 커밋 후 유실된 비동기 작업: 실시간 전송은 RESUME이, 스냅샷은 다음 주기, 리플레이가 보완 |
| **알려진 한계** | 비정상 종료 시 `afterConnectionClosed`가 실행되지 않아 `DISCONNECTED`가 기록되지 않고 presence가 ONLINE으로 남는다. 보완안: 단일 서버는 기동 시 ONLINE 참여자 일괄 `DISCONNECTED`, 다중 서버는 연결별 Redis TTL 하트비트 키 만료 시 기록 |

### ③ DB 장애 / 성능 저하 (커넥션 고갈, 락 경합)

| 단계 | 내용 |
|---|---|
| **감지** | HikariCP 커넥션 대기 시간, 활성 커넥션 수(Actuator 메트릭), 락 대기, 데드락 로그(`SHOW ENGINE INNODB STATUS`), slow query log, 503 응답 비율 |
| **완화** | 락 대기 초과, 데드락은 `503 TRY_AGAIN` + `Retry-After`로 응답(**구현됨**) → 같은 `clientEventId`로 재시도해도 안전. 단 락 대기 상한은 따로 설정하지 않아 MySQL 기본값(`innodb_lock_wait_timeout` 50초)이 적용되므로, 최대 50초를 기다린 뒤에야 503이 나간다. 상한을 짧게 줄이면 커넥션 고갈을 늦출 수 있다. 트랜잭션 안에 외부 호출을 두지 않아(커밋 후 전송) 락 보유 시간 최소화. 비필수 작업(스냅샷)은 대기열 상한(1000)을 두었고, 스레드 수 상한(`max-size`)까지 설정하면 넘치는 작업을 버림. 조회 트래픽은 읽기 복제본으로 분리 |
| **복구** | `EXPLAIN`, slow query log로 원인 쿼리 분석 후 인덱스 보강([4 쿼리 문서](4-queries.md)). 커넥션 풀 크기, 타임아웃 조정. 장애 동안 실패한 요청은 클라이언트 재전송 + 멱등 처리로 자연 복구 |

### 적용 전 500의 원인: 데드락
```
A: INSERT session_event → FK 확인으로 chat_session 행에 공유(S) 락
B: INSERT session_event → 같은 행에 공유(S) 락 (S끼리는 공존)
A: UPDATE chat_session → 배타(X) 락 필요 → B의 S 락 대기
B: UPDATE chat_session → 배타(X) 락 필요 → A의 S 락 대기  → 데드락
```
처음부터 `FOR UPDATE`로 배타 락을 잡으면 같은 세션의 요청이 한 줄로 서므로, 데드락과 seq 충돌이 함께 사라진다. 락은 **세션 행 단위**라 다른 세션끼리는 서로 기다리지 않는다.

| alice 퇴장 후 메시지 | 409 | JOINED가 아니면 메시지 불가 |

| **종료 후** bob 입장 요청 재전송 | **200 (최초 seq, serverTs 그대로)** | 멱등 처리가 검증보다 우선 |

### 자동화된 검증 (JUnit + Testcontainers)

`EventSourcingIntegrationTest`가 위 시나리오를 MySQL 8.4 컨테이너에서 재현한다. 동시성 테스트는 `CountDownLatch`로 20개 스레드를 **동시에 출발**시켜 실제 경합을 만든다.

| 테스트 | 결과 |
|---|---|
| 동시 전송 20개 → seq 3~22 빈틈, 중복 없음, `last_seq = 22` | ✅ |
| 같은 이벤트 동시 재전송 20개 → 신규 1건, 나머지 19건 duplicate, 모두 seq 3 | ✅ |
| 재전송 멱등 / 같은 키 다른 내용 409 / 종료 후 재전송 200 | ✅ |

### 락 제거 실험 (테스트가 실제로 락을 검증하는지 확인)

`ChatSessionRepository.findByIdForUpdate`의 `@Lock(PESSIMISTIC_WRITE)`만 제거하고 같은 테스트를 실행했다.

| 테스트 | 락 있음 | 락 제거 | 실패 원인 |
|---|---|---|---|
| 동시 전송 20개 | ✅ | ❌ | 여러 트랜잭션이 같은 `last_seq`를 읽어 같은 seq(3)를 발급 → `Duplicate entry '…-3' for key 'uk_event_seq'` |
| 동시 재전송 20개 | ✅ | ❌ | 모두 "중복 없음"으로 판단하고 INSERT 경쟁 → `Deadlock found when trying to get lock` (`CannotAcquireLockException`) |

**해석**
- 락이 없어도 **잘못된 데이터는 저장되지 않았다.** UNIQUE 제약(`uk_event_seq`, `uk_event_client_id`)이 최후 방어선으로 막았다.
- 하지만 정상 요청이 **실패 응답**을 받는다. 클라이언트 입장에서는 "보냈는데 실패"가 되어 재시도 폭주로 이어진다.
- 즉 **UNIQUE 제약은 정합성(잘못 저장되지 않음)을, 비관적 락은 정상 처리(모든 요청이 올바른 응답을 받음)를 책임진다.** 둘 다 필요하다.
- 이 실험으로 동시성 테스트가 락의 존재를 실제로 검증하고 있음을 확인했다(락을 빼면 테스트가 잡아낸다).

## 10. 알려진 한계와 개선 방향

| 한계 | 영향 | 개선 방향 |
|---|---|---|
| 연결 목록이 서버 메모리 | 서버 2대 이상이면 다른 서버의 연결로 전달 불가 | Redis Pub/Sub ([5 §5](5-design.md#5-서버-수평-확장--설계)) |
| 서버 비정상 종료 시 presence가 ONLINE으로 남음 | 상대에게 접속 중으로 보임 | 기동 시 일괄 DISCONNECTED 처리, Redis TTL 하트비트 |
| WebSocket 경로에서 DB 제약 위반(`DataIntegrityViolation`)을 처리하지 않음 | 정상 흐름에서는 발생하지 않지만, 발생하면 ERROR 메시지 대신 연결이 끊긴다 (REST는 409 응답) | 핸들러에서 잡아 ERROR 메시지로 응답 |
| 세션 내 `server_ts` 단조 보정 미적용 | `?at=` 변환 쿼리에 정렬(filesort) 발생 | 단조 보정 적용 후 인덱스 역방향 1건 조회 ([4 쿼리 2](4-queries.md#쿼리-2-복원-시각--seq-변환-get-timelineat)) |
| 커밋 후 전송, 스냅샷이 서버 다운 시 유실 가능 | 실시간 전달 누락(→ RESUME이 보완), 스냅샷 누락(→ 리플레이가 보완) | Outbox 패턴 |
