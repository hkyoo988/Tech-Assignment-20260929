# 7. 실시간 통신 방식 비교

## 7.1 후보 비교

| 방식 | 방향 | 특징 | 이 과제에 대한 적합성 |
|---|---|---|---|
| **폴링** (REST 주기 호출) | 클라이언트 → 서버 | 구현 가장 단순 | 지연이 폴링 주기만큼 생기고, 새 메시지가 없어도 요청이 계속 발생 |
| **SSE** (Server-Sent Events) | 서버 → 클라이언트 (단방향) | HTTP 위에서 동작, 자동 재연결, `Last-Event-ID` 지원 | 수신은 좋지만 송신은 별도 REST 필요 |
| **WebSocket** (채택) | 양방향 | 연결 하나로 송수신, 메시지 형식 자유 | ACK·재전송·RESUME 프로토콜을 직접 설계해 보여줄 수 있음 |
| STOMP over WebSocket | 양방향 | 구독/발행, 메시지 브로커 연동 | 브로커 추상화가 편리하지만, 과제의 핵심(ACK·RESUME·멱등)을 프레임워크 규약 안에서 표현해야 함 |
| **WebRTC** | 사용자 ↔ 사용자 (P2P) | 지연이 가장 짧고 서버 부하가 작음. 연결 수립에만 시그널링 서버 필요 | 아래 참고 |

## 7.2 WebRTC(P2P)를 채택하지 않은 이유

| 요구사항 | 서버 중계 (채택) | P2P |
|---|---|---|
| 순서 기준 | 서버가 seq를 한 곳에서 발급 | 양쪽이 각자 기록 → 전체 순서 합의가 어려움 |
| 중복 방지 | 서버가 `clientEventId`로 필터 | 각 클라이언트가 처리 |
| 이벤트 저장·시점 복원 | 서버 DB에 기록 | 별도로 서버에 업로드해야 하고, 업로드 누락 시 복원 불가 |
| 상대가 오프라인일 때 | 서버가 보관 후 재연결 시 전달 | 전달 불가 |

과제의 핵심 요구(순서·중복·복원)가 모두 **단일 기준점**을 필요로 하므로 서버 중계 방식을 택했다.
영상·음성 통화처럼 대용량 저지연 미디어가 필요해지면, **메시지·이벤트는 서버 중계로 유지하고 미디어만 WebRTC로 분리**하는 병행 구조가 적합하다. 이때 WebSocket 연결을 시그널링 채널로 재사용할 수 있다.
